# SpartanCircle: Greenfield campus social matching app

A full Next.js 16 + TypeScript application implementing a student matching, pod grouping, event recommendation, and real-time chat platform for SJSU freshmen and transfers. The architecture is a client-rendered SPA wrapped in App Router route groups, with all data backed by localStorage-persisted mock data. Matching uses a deterministic 100-point weighted scoring system. AI text generation stubs to template-based fallbacks. The demo path (login, dashboard, match detail, conversation starter, chat, pods, events, RSVP) is complete and navigable.

**Watch for:** (1) The auth system has no server-side protection; middleware is a no-op pass-through, so all route protection relies on a client-side redirect that renders `null` during the check (confirmed). (2) The chat system duplicates localStorage key constants and read/write logic across `realtime.ts`, `pod-actions.ts`, and `event-actions.ts`, creating a race condition when concurrent writes target the same key from different modules (confirmed). (3) The matching algorithm's career-goal scoring splits on whitespace and uses a short stopword list, meaning common short words like "engineer", "lead", or "dev" will inflate similarity between unrelated career paths (confirmed).

## High-level view

The matching algorithm is the strongest piece: fully deterministic, weights sum to exactly 100, tests cover each scoring tier, and the breakdown is surfaced through the entire stack from computation to rendered UI. The career-goal dimension is the weakest link due to naive keyword splitting.

Auth and state management is entirely client-side (React context + localStorage). There is no session integrity, no cross-tab coordination, and the middleware file creates false confidence by existing but doing nothing.

The chat system is the most complex subsystem and carries the most technical debt. Three separate modules maintain independent getter/setter pairs for the same localStorage keys, meaning two modules writing to the same key can silently overwrite each other.

The AI text generation functions reference `process.env.OPENAI_API_KEY` (server-side only) but are called from client components, making the OpenAI code path permanently unreachable without an API route layer.

1. **Middleware is a no-op** — Server-side route protection does nothing; client layout redirects but briefly renders nothing. Add a cookie-based session check in middleware or remove the file to avoid false confidence.
2. **localStorage key duplication across modules** — `realtime.ts`, `pod-actions.ts`, and `event-actions.ts` each declare and independently read/write the same keys. Consolidate into a single storage accessor module.

4. **No XSS sanitization on chat messages** — User-generated content flows directly into the DOM via React's JSX escaping, but any future `dangerouslySetInnerHTML` or rich message path would be vulnerable. Document this assumption or add explicit sanitization.
5. **Onboarding state not persisted across refreshes** — The onboarding flow updates localStorage only on completion; if the user refreshes mid-onboarding, state is lost and the form resets.
6. **Non-null assertions on `user!`** — Match detail and other pages use `user!` after a loading guard, but `authLoading` can be false while `user` is still null. Use optional chaining or early return.
7. **No test coverage for chat, onboarding, or safety modules** — All 52 tests target matching logic. The localStorage persistence layer, message sending, and block/report flows have no automated coverage.

## Deterministic matching via weighted scoring

The individual matching algorithm (`score.ts`) distributes 100 points across six dimensions: shared classes (30), same/related major (20), availability overlap (15), shared interests (15), career goal similarity (10), complementary skills (10). The implementation uses step functions rather than linear scaling: 1 shared class = 10, 2 = 20, 3+ = 30. This produces clear tiers but means the difference between 3 and 8 shared classes is invisible.

The career goal scoring at line 99 of `score.ts` is the weakest link:

```typescript
const filteredA = keywordsA.filter((w) => !stopWords.has(w) && w.length > 2);
```

A 3-character minimum means "dev", "ML", "AI", and "UX" are all excluded from matching, while common words like "engineer", "manager", "lead" will match across unrelated goals ("hardware engineer" matches "software engineer" at the same score as two genuinely aligned roles). The stopword list is only 11 words.

Pod scoring (`pods.ts`, `pod-scoring.ts`) uses the same pairwise approach but with different weights (30/25/15/15/15). Both compute all-pairs comparisons, which is O(n^2) per pod. For the mock data size this is fine; for production with thousands of students it would need precomputed caches.

## Client-only auth with no server verification

The middleware is explicitly a no-op:

```typescript
export function middleware(request: NextRequest) {
  return NextResponse.next();
}
```

Route protection happens in the `(main)/layout.tsx` client component:

```typescript
useEffect(() => {
  if (!isLoading && !isAuthenticated) {
    router.push('/login');
  }
}, [isLoading, isAuthenticated, router]);

if (!isAuthenticated) {
  return null;
}
```

The `return null` before redirect means a flash of nothing on protected routes. Since all data is in localStorage, any user can access any mock student's data by manually setting the storage key. The middleware file should either be deleted or documented as intentionally empty to avoid the impression of server-side protection.

## localStorage as shared mutable state

The chat system in `realtime.ts` (410 lines) defines:

```
CONVERSATIONS_KEY = 'spartancircle_conversations'
MEMBERS_KEY = 'spartancircle_conversation_members'
MESSAGES_KEY = 'spartancircle_messages'
```

The pod actions module (`pod-actions.ts`) independently defines and reads/writes the same `CONVERSATIONS_KEY` and member key. `event-actions.ts` does the same. Each module has its own `getStoredConversations()` and `setStoredConversations()` that parse and stringify the same key. If pod-actions writes a new conversation for a pod chat and realtime.ts reads its own stale parsed copy within the same call stack, the pod conversation could be silently dropped.

The fix is straightforward: a single `storage.ts` module that owns all keys and exposes typed accessors.

## Chat context accumulates subscriptions without cleanup

In `context.tsx`, `setActiveConversation` subscribes to realtime updates synchronously:

```typescript
subscribeToConversation(conversationId, (newMessage) => {
  setActiveMessages((prev) => [...prev, newMessage]);
});
```

The cleanup depends on a separate `useEffect` that fires after state updates:

```typescript
useEffect(() => {
  return () => {
    if (activeConversation) {
      unsubscribeFromConversation(activeConversation.id);
    }
  };
}, [activeConversation]);
```

If `setActiveConversation` is called rapidly (navigating between chats), the previous subscription's cleanup fires only after the new subscription is already created. In mock mode the subscription is a no-op, but once Supabase is connected, each rapid navigation would stack up Postgres channel subscriptions until the effect catches up.

## Non-null assertions in pages

The match detail page uses `user!` in multiple places:

```typescript
<SharedAvailability
  availabilityA={user!.availability}
  availabilityB={matchedStudent.availability}
/>
```

The loading guard returns early when `authLoading` is true, but there's a timing gap: `authLoading` can be false while `user` is still null (between the effect setting `isLoading` to false and setting `user`). This produces a runtime error. The same pattern appears in the dashboard and pod detail pages.

## Unreachable OpenAI code path

The `isOpenAIConfigured()` check in `src/lib/ai/index.ts` reads `process.env.OPENAI_API_KEY`, which is a server-side env var. These functions are called from client components (match detail page). In Next.js, `process.env` without `NEXT_PUBLIC_` prefix is undefined in browser bundles, so `isOpenAIConfigured()` will always return false on the client. The OpenAI integration path is unreachable from the current call sites even when the key is configured. The functions would need to move behind an API route.

## PWA cache expiration gap

The service worker uses cache-first for static assets with no TTL or cache-busting logic. Next.js uses content-hashed filenames for JS bundles, so this is safe for chunked JS. But images or fonts served without hashed names would be cached indefinitely, causing stale assets after deploys.

## Test coverage gaps

All 52 tests target `src/lib/matching/`. Not tested: the entire localStorage persistence layer, message sending/receiving, conversation creation, block/report actions, onboarding state management, and auth context behavior. The chat module's complexity (410 lines with interacting state functions) would benefit most from integration tests.

## Missing RLS policies for Supabase migration

The SQL schema (`001_initial_schema.sql`) defines tables, enums, indexes, and constraints matching the TypeScript types, but contains no Row Level Security policies. When the app moves from mock mode to a live Supabase instance, every table will be publicly readable/writable until RLS is enabled and policies are added.
